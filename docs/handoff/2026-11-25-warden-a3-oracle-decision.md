# Warden: разбор второй попытки A3 и решение по §8/§9 оракулу (WOTR-D-047)

Дата: 2026-11-25. Основание: разбор Coordinator'а по второй попытке A3
(`41f6f0cf-5705-8170-bd35-c3a330ee8e37`, seq 8, Integration Auditor, ветка
`arena/741a3d19-open-bfme`) и вопрос «какой оракул должен быть у §8/§9». Ответ:
**оракул остаётся прежним («in Arena», §9), гейт-блокер §9.2 устранён инструментально,
формулировка выдачи A3 меняется** — ниже.

## 1. Вторая попытка A3 — разбор

Возврат в «Rework» по D-045 сохранён. Попытка 2 провалена уже по форме:

- ветка `arena/741a3d19-open-bfme` не отправлена в origin — PR нет,
  `docs/evidence/WOTR-1-1/A3/**` не имеет якоря в репозитории, рабочее дерево сэндбокса
  приёмочным артефактом не является;
- `report.md` не записан (таймаут), «разовый отчёт в конце» снова не сработал;
  «Report SHA» остался `inline` — это прямое нарушение условия D-045
  (литеральный путь `docs/evidence/WOTR-1-1/A3/report.md`);
- причина остановки сборки (`subcommand failed` после ~2228/2618 целей) не извлечена в
  отчёт: ни rc, ни строки ошибки — фатально для разбора и запрещено условиями приёмки;
- утверждение «не редактировал Notion по вашей инструкции» не соответствует фактам —
  инструкции не редактировать Notion не было, а отчёт при этом держал Dispatch State
  `Running` вопреки состоянию карточки (`Rework`, `Check=fail` с 13:43).

Замечание: даже без дефектов формы попытка не могла закрыть §9.2 — см. §2. Требование
Coordinator'а «не перевыдавать третий раз в той же формулировке» принято: формулировка
меняется в §4.

## 2. Гейт-блокер §9.2 — структурный, и он устранён

Факты (проверены по репозиторию):

- `openbfme_tests` несёт MP3-часть `test_audio_decode` поверх синтетических фикстур
  `tools/audio/gen_mp3_fixtures.py` → `<build>/audio_fixtures/*.mp3.bin`. Без фикстур
  `test_audio_decode.cpp:830 REQUIRE(problem.empty())` фатален → rc 1 бинаря при любой
  сборке. Это гейт по дизайну: строки `*.mp3.bin` никогда не коммитятся (retail-format
  байты, включая синтетические, остаются вне git), закреплены только контракты
  `engine/tests/data/audio/mp3_fixtures.tsv` (sizes + SHA-256) и `mp3_golden.tsv`.
- CI-джоб `Reference MP3 fixtures` ставит `apt-get install lame mpg123` и генерирует
  фикстуры. Песочница без root и без apt ставить их не может → требование
  «full gate exit 0 in Arena» было недостижимо в текущей формулировке. Отсюда же: ни
  одна попытка не лгала про «зелёный `openbfme_tests` в песочнице» — K7 честно давал
  1925/1926 на фокусированном бинаре, K6 честно красный.

**Устранение (гейт не ослаблен):**

- бандл `wotr-audio-fixtures.tar.gz` (17 потоков `*.mp3.bin`) загружен в
  `Arena/wotr-remaster/artifacts`, Drive file id `1AQYEUURZn3dZJ8WJp8DjnmVfa0RGMzku`,
  SHA-256 архива `1e58106afd3ebf8f535b8aa11a040a29665051b0266caddc1984ccdfdf6ea052`;
- доверие даёт не бандл, а манифест в git: каждый прогон обязан выполнить
  `python3 tools/audio/gen_mp3_fixtures.py --check-only --out <каталог>` → rc 0 и строка
  `Verified 17 MP3 fixtures (sizes and SHA-256)` — сверка каждого файла с закреплённым
  манифестом; команда, rc и вывод входят в доказательство (cost-gates §5.1);
- запуск тестов: `OPENBFME_AUDIO_FIXTURES=<каталог> …/openbfme_tests` — каталог вне
  `engine/build` (его `--clean` удаляет);
- происхождение бандла (однократное, 2026-11-25, инструментарием процесса): дерево
  релиза lame-3.100 (GitHub-зеркало релиза), `./configure && make`,
  `LAME 64bits version 3.100`, генерация по `FIXTURES` самого генератора, сверка
  `--check-only` — совпадение байт-в-байт с закреплённым манифестом. CI-джоб остаётся
  эталонной перегенерацией (lame 3.100 + mpg123 1.33.1); `--write-golden` в прогоне
  запрещён.

Таким образом §9.2/§9.13 снова достижимы in Arena: «fail 0» полного `openbfme_tests`
остаётся обязательным условием и становится выполнимым.

## 3. Три варианта — решение

1. **Пинованный зелёный CI как доказательство §9.2 (sandbox только §9.3–§9.13) —
   отклонён.** Оракул §9: «in Arena» — это требование доказательства, а не побочный
   эффект. Снижать планку нельзя; CI (`5b8c5f3`, 16/16) включается в отчёт как
   корреляция (поля «C++/Godot test summaries» §9 и так её ожидают), не как замена
   arena-команды с rc. Раз гейт-блокер устранён, нужды в замене нет.
2. **Разделение A3 на build-карточку и launch-карточку — отклонён.** §8: «A3: auditor
   performs §9 exactly» — одна карточка = один честный прогон всей цепочки на одном
   принятом SHA в clean checkout. Split правил бы §8/§9 ради логистики и размывал бы
   claim «один SHA — весь оракул». Причина непрохождения была не в объёме, а в блокере
   (§2) и в форме отчётности (§1, §4) — оба адресованы. Вопрос объёма может быть
   поднят заново только с фактическими замерами шагов, если третий прогон при
   устранённом блокере покажет перерост по времени.
3. **Retail-reuse + persisted-снимки — принят, с уточнением границ.** Уже действует:
   cost-gates §5 «Повторный агент в том же workspace переиспользует провалидированную
   `.retail`, а не скачивает её заново» — третий прогон продолжает тот же dispatch
   (рабочее дерево и `.retail` сохраняются). Инструментальные снимки
   `tools/arena/build_cache.py` (identity: дерево, godot-cpp pin, компилятор) разрешены
   для итераций; «never an acceptance gate» остаётся в силе: приёмка опирается на
   команду/rc/вывод шага (`build_engine.sh --tests`, `openbfme_tests`) на принятом SHA,
   а не на снапшот. Правила гидратации retail не меняются: canary → шаги ≤5 томов →
   удаление staging-parts → переиспользование `.retail` до конца прогона (OOM-дисциплина
   обязательна). Гидратация фикстур (§2) не имеет tier'а стоимости и выполняется до
   §9.2/§9.13.

## 4. Изменённая формулировка выдачи A3

Условия возврата D-045 остаются в силе целиком: та же карточка, seq 8, Integration
Auditor; полный §9 на одном принятом SHA в clean checkout; §9.2/§9.4/§9.5 с записанными
результатами (не `not run`); «Report SHA» = `docs/evidence/WOTR-1-1/A3/report.md`;
cost gate build full + retail hydrate; без test hooks, липовых результатов, mock-ов
провайдеров. Дополнение (это и есть изменение формулировки):

- **Шаг фикстур** перед §9.2/§9.13: гидратация `wotr-audio-fixtures.tar.gz` по
  cost-gates §5.1 + `--check-only` с rc 0 в доказательстве. «fail 0» полного
  `openbfme_tests` — обязательное условие §9.2/§9.13.
- **Ветка пушится в origin сразу после первого commit** — раньше, чем отчёт.
  Несдвинутая ветка = потерянная попытка (так погибла попытка 2); рабочее дерево
  сэндбокса не является приёмочным артефактом.
- **`report.md` коммитится в день выдачи** (шаблон + заголовок) и дополняется по мере
  прогонки шагов; «разовый отчёт в конце» запрещён. Каждый шаг §9 фиксируется в отчёте
  сразу после прогона: cost gate (tier), команда, rc, вывод, SHA. Падение сборки —
  rc и строка ошибки в отчёт немедленно.
- **«Report SHA» = `docs/evidence/WOTR-1-1/A3/report.md`** — литеральный путь; `inline`
  запрещён.
- **«Для нас» — только в «Обновление для Мастера»** (D-044); команды исполнителю —
  только из правила роль→команды; отчёты «Свободно»/«Разбор задач» — только от
  Transport; Dispatch State карточки не редактируется аудитором.
- **Retail**: полная гидратация от пинованных томов (canary → шаги ≤5) или
  переиспользование провалидированной `.retail` того же dispatch'а; снапшоты
  `build_cache.py` — для итераций, не для гейта.

Третья выдача: Coordinator переводит A3 из `Rework` с блоком выше (новая формулировка).
Приёмщик судит шаги по отчёту — «not run» в любом шаге остаётся основанием возврата.

## 5. Признание

Warden (мастерская процесса): оракул §8/§9 не изменён; гейт-блокер §9.2 устранён
инструментально (бандл из Drive + обязательная сверка `--check-only` с манифестом в
git); CI принят как корреляция, не как замена §9.2; retail-reuse подтверждён с границами
`build_cache.py`; формулировка выдачи A3 изменена как в §4. Далее — Coordinator
перевыдёт A3; Def-A1-1/2/3 продолжаются независимо. WOTR-D-047.
