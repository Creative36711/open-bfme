# Сборка бандла ScriptCat этим репозиторием

Решение — `docs/DECISIONS.md`, запись `WOTR-D-033`; правило — §1 и §15 `docs/REGULATION.md` (с версии 1.6).

Транспорт (`Creative36711/relay-wotr`) — одна библиотека на много проектов. Он не хранит наших
документов, не читает наше дерево и не подстраивается под проект. Бандл, который получают агенты,
собираем мы: `tools/relay/build.mjs` скачивает запиненный выпуск, два раза разворачивает снимок —
один раз для **нейтральной** сборки (её sha256 обязан равняться `pin.transport.artifact.sha256`:
так проверяется, что запинен именно проект-нейтральный артефакт, а не чужой регламент внутри),
второй раз — для сборки с нашим входом `--digest docs/regulation-digest.md`, который получает
**его** `tools/script-cat/build.mjs`. Проверки допускает **его** узел `tools/relay-build.mjs`, а не
наш список. Профиль проекта сборке не передаётся: `project-profile.json` — импорт-файл рантайма
ScriptCat, он лежит здесь и живёт в их `publicProjectFiles` (см. `docs/setup/notion-ids.md`).
Правка регламента не создаёт задач в транспорте и не требует синхрон-PR туда.

## Файлы

| Путь | Что хранит |
|---|---|
| `pin.json` | запиненный выпуск: репозиторий, коммит (или тег), `@version`, `contractVersion`, sha256 архива снимка, путь и sha256 нейтрального артефакта + `embedsRegulation: false`, пути наших входов и артефактов |
| `build.mjs` | узел сборки: скачивание → сверка хешей → нейтральная сборка → сборка с `--digest` → его проверки → `build/relay/` |
| `project-profile.json` | профиль проекта для транспорта; байт-в-байте копия их бывшего `tools/script-cat/wotr-project.json`, чтобы перенёс файл, а не переписал значения |
| `deploy.json` | наш деплой: целевой Apps Script и назначение артефакта. Только здесь, только наше |
| `relay_test.mjs` | тесты узла (`node --test tools/relay/relay_test.mjs`), герметичные: сеть подменяется, кэш — временный каталог |

Артефакты — в `build/relay/`: `relay.user.js`, `prompt-coverage.json`, `build-manifest.json`
(без меток времени: два запуска обязаны давать байт-в-байт одинаковые файлы, иначе сверять
установленный бандл нечем).

## Команды

```bash
node tools/relay/build.mjs              # собрать и допустить (или отказать)
node tools/relay/build.mjs --check      # два запуска, сверка байтов: детерминизм
node tools/relay/build.mjs --verify     # проверить собранный артефакт без сети
node tools/relay/build.mjs --json       # машинный отчёт в stdout
node tools/relay/build.mjs --offline    # только из кэша (нет кэша — код 3)
node --test tools/relay/relay_test.mjs  # тесты узла
```

Коды возврата как у узла транспорта: `0` — допущено, `1` — неверный запуск или негодный пин,
`2` — проверка не пройдена (сборка не допущена), `3` — источники или входы не получены. Отказ
всегда объясняет причину; ни одна проверка не превращается в `pass`, если её не удалось выполнить.

Что именно считается достаточным основанием отказа: sha256 снимка ≠ запиненный; в снимке нет
`tools/script-cat/build.mjs` или `tools/relay-build.mjs`; нейтральная сборка ≠
`pin.transport.artifact.sha256` (или, наоборот, бандл с регламентом совпал с нейтральным артефактом
— значит вход не подставился); их `contracts/build-manifest.json` не зафиксировал наш digest либо
зафиксировал другие байты/номер; вшитый в бандл регламент ≠ наш `docs/regulation-digest.md`
после их же правила нормализации; номер во вшитом регламенте ≠ шапка `docs/REGULATION.md`;
`@version` ≠ запиненный; `docs/` снимка содержит наш регламент (D-003 нарушен); узел транспорта
вернул отчёт без списка проверок или не допустил сборку.

`--verify` проверяет артефакт без сети и независимо от пина, поэтому он обязан падать на артефакте,
собранном до D-003 (в его манифесте нет `project.transportManifest` — он сверял равенство двух
наших файлов, а не принятие входа их сборкой).

## После выпуска транспорта (перепин)

```bash
git -C <клон relay-wotr> rev-parse main                      # коммит, который принимаем
node tools/relay/build.mjs                                    # соберёт и покажет расхождение
```

`pin.json` обновляется пятью полями: `transport.commit`, `snapshot.sha256` (берётся из скачанного
архива; `build.mjs` печатает ожидаемое и фактическое значение в причине отказа), `userscriptVersion`
из `@version` принятого выпуска и `artifact.sha256` нейтрального `tools/script-cat/relay.user.js`
на этом коммите (`embedsRegulation` остаётся `false`). `contractVersion` — `protocolVersion` из
`tools/script-cat/contracts/agent-protocol.json`. Перепин — обычный PR с гейтом `build: full`: бандл,
собранный нами, обязан пройти `--check`.

## Деплой

Принятый `build/relay/relay.user.js` вставляется в проект Apps Script `deploy.json.target`
(`wotr-remaster-relay`), публикуется версия, соответствующая `@version` бандла; userscript в
браузер устанавливает человек. `build-manifest.json` — то, что прикладывается к evidence: по нему
видно, какой выпуск транспорта, какие байты нашего регламента (и что их сборка это подтвердила) и
какой отпечаток попали в установку.

## Границы

- Мы не правим дерево транспорта: только читаем запиненный снимок и подаём ему свой регламент.
- Транспорт не читает наш репозиторий и не хранит наших документов: ни `open-bfme`, ни `WOTR-*`, ни
  наши Notion/Drive ID в его дереве — это проверяют их `portability-guard` и `check:docs`.
- Кэш снимка живёт вне рабочего дерева (по умолчанию `$TMPDIR/wotr-relay-cache`): узел транспорта
  определяет проверяемое дерево по `git status`, и кэш внутри репозитория заставил бы его проверять
  наше дерево и отказывать. Проверка вшита в `assertCacheOutsideRepo`, а не оставлена на удачу.
- `@version` бандла при нашей правке docs не меняется и не должен: он говорит о выпуске транспорта.
  Идентичность сборки проекта — `artifact.bundleSha256` в манифесте.
